Цель: Исследовать затраты времени на компиляцию C++-сервиса на базе userver с помощью Clang Build Analyzer, определить наиболее дорогие операции компиляции и проверить гипотезу об ускорении сборки.

Мой ПК: Ubuntu 24.04.4 LTS. Процессор: AMD Ryzen 7 5800H, оперативная память: 16.0 GB, архитектура: x86_64.

Сам сервис собирался не прямо в хостовой системе, а внутри Docker-образа ghcr.io/userver-framework/ubuntu-22.04-userver с digest sha256:fca9c8ac7e97b4e2b042d822facbb152aec10a9d4e09c0862e44c50640f3f303.
Для контейнера были заданы ограничения из условия: четыре CPU (ядра 0–3) и 8 ГБ памяти вместе со swap. Внутри использовались Clang 14.0.0, CMake 4.4.4, стандарт C++20 и профиль Release. Для анализа времени компиляции использовался Clang Build Analyzer 1.6.0.
При этом внутри контейнера не было по дефолту clang 14, пришлось устанавливать самому

Сначала я просто запустил сборку, она у меня упала на процессе линковки, но это не помешало прочитать получить анализ от Clang Build Analyzer.
Получилось, что файлы скомпилировались за 34.8 с. Важно отметить, что по времени работы frontend больше всего у src/main.cpp и сгенерированных файлов hello_client.usrv.pb.cpp hello_service.usrv.pb.cpp.
При этом по backend сгенерированные hello_client.usrv.pb.cpp hello_service.usrv.pb.cpp затратили больше, чем main.cpp.

Среди шаблонов выделяется std::unique_ptr: суммарно 1,604 с по 177 инстанцированиям.

Я покапался в хедер файлах src/hello_postgress.hpp, src/hello_grpc.hpp, потому что они в анализе были отмечены как самые "тяжелые" хедеры.

Что я заметил
```
hello_postgres.hpp:
#include <userver/components/component.hpp>
#include <userver/server/handlers/http_handler_base.hpp>
#include <userver/storages/postgres/cluster.hpp>
```
Здесь есть потенциально интересный момент. Типы ComponentConfig и ComponentContext используются в объявлении конструктора только как константные ссылки:
```
HelloPostgres(const userver::components::ComponentConfig&, const userver::components::ComponentContext&);
```
В C++ для объявления функции с параметрами-ссылками часто достаточно предварительно объявить классы, не подключая заголовок с их полными определениями. А это как раз описано в component_pwd.hpp.
А в userver/components/component.hpp определяются и class ComponentConfig, и class ComponentContext. А hello_postgress.cpp по сути нужен только ComponentContext.
Есть гипотеза, что если подключить только нужные файлы, то время сборки уменьшится.

Эксперимент:
В заголовке hello_postgres.hpp полный заголовок component.hpp заменён на component_fwd.hpp. Полное определение ComponentContext подключено в hello_postgres.cpp.
В отчёте Clang Build Analyzer число учтённых включений component.hpp уменьшилось с 4 до 3, а суммарные затраты на обработку этого заголовка — с 2,684 до 1,841 секунды.
При этом суммарные метрики frontend и backend выросли с 34,8 до 42,9 секунды. Мне показалось это странным и я попробовал еще несколько раз, но все равно сборка с изменениями компилируется дольше, чем обычная.
Важно отметить, что линковка во второй раз прошла нормально. Точную причину сбоя в первый раз я не выяснил, но могу предположить, что, возможно, не хватило выделенной контейнеру оперативной памяти.

Вывод: Изменение в файлах сократило число подключений component.hpp, но ускорение всей сборки не подтвердилось. К сожалению, скорее всего, экперимент провальный.
